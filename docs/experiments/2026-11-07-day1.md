# 2026-11-07 第一天：工程底座与 A1 最小闭环

## 假设

在没有框架的情况下，用一屏代码的循环 + 四个只读工具，就能跑通"统计仓库 TODO/FIXME"这类任务；
把 trace 与成本计量放进第一版，比后面补更省事。

## 改动

- 建仓：git init -b main，按表6 建 llm / tools / loop / trace / cli 五个目录，加 tests、docs、scripts。
- 依赖：uv 管理，运行时 httpx、openai、pydantic、rich，开发 pytest、ruff（行宽 100）。
- 模型层：base 协议 + doubao（流式、取真 usage、429 指数退避 1/2/4 秒、关闭 SDK 自带重试）+ fake。
- 工具层：注册表按 pydantic 生成 schema，四个工具 read_file、search_files、run_shell、finish；
  run_shell 只放行 git/rg/python/pytest/uv/ruff，git 的 push/reset/clean 直接拒，超时 10 秒；
  输出超过 4000 字符时显式标注"已截断"，search_files 扫完全量再按上限展示并给出命中总行数。
- 循环：最多 12 步，同一工具同参数连续 3 次即停，finish 收尾；系统提示固定六条纪律
  （单步单工具、单一计数口径、截断必须重取、优先 search_files、Windows 命令限制、信息够了必须收尾）。
- 追踪：traces/*.jsonl，事件为 llm / tool / finish / loop_guard / run_end，
  llm 事件带 usage（含 cached）、attempts、first_byte_ms、cost_yuan。

## 结论

骨架可用。三次端到端暴露的三个问题都不是模型能力问题，而是工程缺口：

1. 输出静默截断。run_shell 把 stdout 直接切到 4000 字符、search_files 命中即停，
   模型把"部分结果"当成全量，于是 FIXME 从 9 行报成 7 行，还把 15 + 7 相加得 22。
   修法：截断必须留标记，search_files 扫完再展示并报总行数。
2. 工作区污染。仓库根留着上一次的 e2e 输出与 trace，正则把它们也算进命中，
   模型越查越乱。修法：out/ 与 traces/ 进忽略清单并被 search_files 跳过。
3. 口径不唯一。系统提示没约束"总数等于明细条数"，模型混用 rg -n 与 rg -c 两种口径。
   修法：提示里固定单一计数口径，并禁止截断结果下总数。

成本核算需要单独说明：usage 里的 cached_tokens 按 0.016 元/百万计价，命中前缀缓存后
输入单价大幅下降，所以 19303 token 只花 0.010557 元；不记 cached 就对不上账，已补进 trace。

## 第四轮：计价缺陷与修正

发现：trace 里的 cost 与手算对不上。根因是 recorder 把三档单价写成模块级常量，
导入时求值，早于 .env 加载，所以 ARK_PRICE_* 从未生效，一直按旧档的 6 / 30 / 1.2 计算。

修法：改为 `prices()` 函数，每次调用时读环境变量，默认值直接写当前模型的 0.8 / 3.2 / 0.016；
补四条单测覆盖默认值、三档相加、改环境变量后生效、缓存命中不全价计费。

验证：重跑同一任务，8 步 finished，输入 25982、输出 4763、缓存命中 20096，trace 记 0.020272 元；
手算 5886×0.8 + 20096×0.016 + 4763×3.2 = 20271.9（十万分之一量级一致）。

影响：本轮之前的 0.010557 与 0.035932 两个数字按旧单价算出，不能与本次直接比较；
此后一律以 trace 内 cost_yuan 为准，跨轮比较只看单价相同的数据。
